# مصفوفة سياسة التفويض — معتمدة

**الحالة:** اعتمدها المستخدم في 2026-10-23. المصفوفة تصف السياسة المستهدفة، بينما يوضح دليل الأمان ما نُفّذ فعليًا.  
**الغرض:** إغلاق قرارات التفويض قبل بدء تعديل التطبيق والاختبارات.  
**المرجع التشغيلي:** `docs/project-tracking/authorization-worklog.md`  
**مبدأ التنفيذ:** لا تُضاف استثناءات للأدوار داخل المتحكمات مباشرة؛ تُنفّذ السياسة في طبقة مركزية، وتُختبر على SQLite وMySQL.

## 1. القرارات التي اعتُمدت سابقًا

1. لا نضيف حالة lifecycle باسم `published` في هذه المرحلة.
2. إتاحة Blueprint النظام للعامة تتطلب اجتماع: ملكية نظام صحيحة، `lifecycle_status=active`، مراجعة حالية موجودة ومجمّدة، و`policies.visibility=public` في المراجعة الحالية نفسها.
3. لا تكفي `active` وحدها أو `visibility=public` وحدها للإتاحة.
4. لا يُعرض `draft` أو `deprecated` أو `sunset` في discovery العام، ولا يسمح بتنفيذ جديد لها من مستخدم عادي.
5. لا تُكشف `logic` و`contracts` و`outputs` و`policies` في discovery العام.
6. Blueprint المستخدم الخاص يبقى تحت سيطرة مالكه، ولا يُمنح الآخرون حق الوصول إليه لمجرد معرفة المعرّف.
7. discovery والتنفيذ التعليميان يجب أن يعتمدا على مصدر أهلية واحد للأدوات المنشورة، لا على namespace وحده.
8. لا نغيّر حاليًا سلوك `nullOnDelete()` قبل اعتماد سياسة الاحتفاظ ببيانات التنفيذ.
9. لا يبدأ تعديل كود التطبيق أو الاختبارات قبل اعتماد هذه المصفوفة.

## 2. تعريف الأدوار

| الدور | المعنى المستهدف |
|---|---|
| `guest` | زائر غير مصادق؛ لا ينفذ عمليات تتطلب حسابًا أو بيانات خاصة. |
| `user` | مستخدم مصادق؛ يدير موارده ويستخدم الموارد العامة المؤهلة. |
| `admin` | مسؤول بصلاحيات إدارية محددة وممنوحة صراحة، وليس وصولًا شاملًا تلقائيًا. |
| `super_admin` | مسؤول أعلى يستطيع إدارة صلاحيات الإدارة والاستثناءات المركزية وفق ضوابط قابلة للتدقيق. |

**الحالة التنفيذية:** أضيفت حقول الدور والصلاحيات وسياسة التفويض المركزية وواجهات الإدارة الأساسية. أضيفت لوحة إدارة عربية أولية في PR #313، وتنتظر نجاح CI قبل الدمج.

### قيود لا يجوز تجاوزها بواسطة الدور

- المراجعة التي يجري تنفيذها يجب أن تنتمي إلى Blueprint نفسه.
- يجب أن تكون المراجعة مجمّدة وحالية، وأن تكون حالة Blueprint مؤهلة للتنفيذ.
- لا يُسمح بترقية مراجعة أقدم لإحداث rollback؛ الترقية تتقدم إلى مراجعة أحدث فقط.
- لا ينبغي أن يغيّر التفويض الإداري invariants الخاصة بسلامة البيانات أو العلاقات المرجعية.
- لا تُكشف تفاصيل التنفيذ أو سجلات المستخدمين لمجرد وجود دور إداري عام؛ يلزم إذن منفصل ومحدد.
- يجب أن يكون رفض الوصول ثابتًا عبر كل المسارات، لا عبر واجهة الويب فقط.

## 4. عقود القراءة والاكتشاف المقترحة

### 4.1 Discovery العام

اقتراح أولي للاستجابة العامة:
- `canonical_name`
- `title`
- `description`
- تصنيف/وسوم منتقاة ومسموح بها صراحة
- `version` أو رقم المراجعة المنشورة

لا تتضمن الاستجابة: `id` الداخلي عند عدم الحاجة، أو `namespace` الداخلي، أو الملكية، أو lifecycle الداخلية، أو `logic`، أو `contracts`، أو `outputs`، أو `policies`، أو metadata كاملة.

### 4.2 Teacher discovery

يبقى عقدًا منفصلًا متخصصًا:
- `slug`
- `title`
- `purpose`
- `target_level` اختياري
- `version`

يجب أن يستند الاكتشاف والتنفيذ إلى سجل/سياسة أدوات تعليمية معتمدة واحدة. لا يكفي وجود العنصر في namespace `skillvlt.edu.assessment`.

### 4.3 قراءة تفاصيل المراجعة

الافتراضي المقترح:
- المالك يستطيع قراءة تفاصيل مراجعات Blueprint المستخدم الخاص به.
- المستخدم الآخر لا يستطيع قراءة أي تفاصيل خاصة.
- المستخدم العادي لا يقرأ تفاصيل المراجعات الداخلية لـBlueprint النظام، حتى لو كان Blueprint متاحًا للاستخدام العام.
- يمكن توفير endpoint منفصل لبيانات وصفية عامة، بدل إرجاع كائن Blueprint الكامل.
- وصول الإدارة للمراجعات الداخلية يكون بصلاحية منفصلة ومحددة، لا نتيجة كون المستخدم `admin` فقط.

## 5. القرارات التي اعتمدها المستخدم

### القرار A — معنى public في MVP

**القرار المعتمد:** تعني `public` أن أي مستخدم مصادق داخل SkillVLT يستطيع اكتشاف المورد واستخدامه وفق الشروط؛ تبقى API الحالية خلف `auth:sanctum`. فتح discovery للزوار غير المصادقين قرار مستقل لاحق.

السبب: جميع مسارات API الحالية، بما فيها discovery، داخل `auth:sanctum`. تغييرها إلى وصول مجهول يوسّع سطح الهجوم والعقد العام دون ضرورة مثبتة.

### القرار B — صلاحيات admin

**القرار المعتمد:** صلاحيات مفوضة ومحددة، مثل:
- `blueprint.system.create`
- `blueprint.user.read_private`
- `blueprint.user.execute_private`
- `blueprint.system.read_private`
- `blueprint.system.manage_revisions`
- `blueprint.system.manage_lifecycle`
- `teacher_tools.manage_registry`
- `execution.support_read`

لا يُمنح `admin` تلقائيًا جميع هذه الصلاحيات. تُسجّل عمليات تجاوز الخصوصية مع السبب وهوية المسؤول.

### القرار C — صلاحيات super_admin

**القرار المعتمد:** يملك إدارة الأدوار والمنح والاستثناءات المركزية، لكنه لا يتجاوز قيود سلامة البيانات. أي قراءة لمحتوى خاص أو سجل تنفيذ يجب أن تكون صريحة، مبررة، وقابلة للتدقيق.

### القرار D — سياسة سجل Execution عند حذف المستخدم

**القرار المعتمد:** عند حذف المستخدم:
- يبقى سجل التشغيل الأدنى اللازم للتكامل المرجعي والتدقيق.
- يصبح `owner_id=null` ولا يعود متاحًا عبر قراءة المستخدم العادية.
- تُمحى أو تُجهّل `input` و`context` و`output` وأي `error` قد يحمل بيانات شخصية، ما لم توجد ضرورة احتفاظ موثقة.
- تُحدد مدة احتفاظ واضحة قبل إطلاق سياسة الإنتاج.

تم تنفيذ تجريد البيانات عبر حدث حذف نموذج User في PR #308. يجب أن تمر عمليات الحذف عبر Eloquent؛ الحذف المباشر عبر SQL يتجاوز الحدث ولا يطبق التجريد.

### القرار E — توافق discovery العام

**القرار المعتمد:** تقديم عقد عام محدود ومعلن، مع إبقاء قبول metadata المرن في طبقة المجال كما هو. تُحصر التغييرات في projection/API، وتضاف اختبارات عقد؛ وإذا كان هناك مستهلك خارجي يعتمد على الحقول الحالية، يُوفّر انتقال توافق موثق بدل إزالة مفاجئة.

## 6. السلوك الحالي مقابل الهدف

| المجال | السلوك الحالي بعد PR #308 و#309 | المبدأ المستمر |
|---|---|---|
| المصادقة | معظم API تحت `auth:sanctum`؛ login عام مع throttle | الإبقاء على المصادقة في MVP |
| الأدوار | `role` و`permissions` موجودان؛ admin يحتاج صلاحية صريحة؛ super_admin وحده يدير الأدوار | least privilege وسجل تدقيق |
| قراءة تفاصيل system | المستخدم العادي يرى metadata العامة فقط؛ التفاصيل تحتاج المالك أو صلاحية مدققة وسببًا | عدم كشف logic/contracts/outputs/policies عبر القراءة العامة |
| تنفيذ system | المستخدم العادي يحتاج شروط public كاملة؛ الاستثناء الإداري يحتاج صلاحية وسببًا وسجل تدقيق؛ المحرك يفرض lifecycle/revision invariants | فصل التفويض عن invariants المجال |
| Teacher discovery | يرشح discovery العام بسجل أدوات المعلم وسياسة الرؤية | المصدر نفسه للاكتشاف والتنفيذ والعرض |
| Teacher execution | slug مسجل + system-owned + active + current frozen + public | namespace وحده لا يمنح الأهلية |
| سجل التنفيذ | المالك يقرأ سجله؛ دعم إداري يتطلب execution.support_read وسببًا؛ حذف المستخدم عبر Eloquent يجرد payload ويترك سجلًا أدنى | العزل وتقليل البيانات واستمرار سجل التدقيق |
| metadata | discovery العام يعيد canonical_name/title/description/category/tags/version فقط | الحفاظ على عقد محدود وتوافق موثق |

## 8. معايير القبول

- لا يستطيع تغيير المعرّف أو slug أو namespace تجاوز التفويض.
- كل عملية قراءة/تعديل/تنفيذ تتحقق من الملكية والرؤية والحالة والصلاحية المناسبة.
- لا يتسرب من discovery أي حقل تنفيذي داخلي أو metadata كاملة.
- teacher discovery والتنفيذ متسقان مع سجل الأهلية نفسه.
- الاختبارات تغطي السماح والمنع، بما فيها الحالات السلبية والـIDOR ومحاولات الوصول إلى موارد system/private/unpublished.
- جميع الاختبارات تمر على SQLite وMySQL.
- وثائق التنفيذ النهائية تميّز بوضوح بين السلوك الفعلي، والسياسة المستهدفة، والقرارات المؤجلة.
